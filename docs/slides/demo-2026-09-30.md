# The problem

We want teams to use agents to **modernize applications at scale.**

Define an agent once, then run it across an application inventory.

The people running it need to be able to follow its progress, review its
work, and use it without having built the agent themselves.

<!--
Our starting use case is application migration. We need to make that
repeatable across an inventory and accessible through Konveyor.
-->

---

# The landscape

- **Agent Sandbox** provides sandbox lifecycle and isolation. We build on it.
- **OpenShell** adds policy enforcement and model access. Integration is our next step.
- **Lightspeed agentic operator** focuses on cluster remediation.
- **Kagenti** provides security and networking middleware for deployed agents.
- **Fullsend** runs autonomous development workflows on GitHub Actions.

We needed reusable agents and workflows that teams could run across an
application inventory.

<!--
The comparison is documented in konveyor/enhancements#295:
https://github.com/konveyor/enhancements/pull/295

The project named there is Kagenti, not kagent. Avoid generalizing these
projects as long-running agents; they solve different problems.

Lightspeed's LLMProvider covered our provider requirements. Its Agent
configuration did not bundle the image, prompt, and skills we needed.
OpenShell's SDK was not available when we started, so we introduced a
Gateway CRD as an interim provider/model configuration.

# What we built

Define the building blocks once, then reuse them across runs:

- **Gateway** configures one LLM provider and model: endpoint, credentials, and context window.
- **SkillCard** supplies one skill or rule. Skills load on demand; rules are included in the prompt.
- **SkillCollection** groups related skills so an Agent can reference them together.
- **Agent** combines an image and toolchain, prompt, skills, permitted Gateways, and default execution limits.
- **AgentWorkflow** combines Agents into ordered stages, with a shared guide and instructions for each stage.

<!--
Build from model access to skills, then agents, then workflows.
Skills use the Agent Skills SKILL.md format and can come from OCI images,
git, or inline content. They carry knowledge and instructions.
Creating an Agent or AgentWorkflow defines a template; it starts no work.
-->

---

# Multi-stage workflows

**AgentWorkflow** defines the stages. Each stage references its own **Agent**.
Konveyor's `java-ee-to-quarkus` workflow:

| Stage | Agent | What it does |
|---|---|---|
| **plan** | migration-plan-agent | Reads analysis and writes a migration plan |
| **execute** | migration-execute-agent | Applies the plan and records a handoff |
| **verify** | migration-verify-agent | Builds, fixes compilation errors, and runs tests |

- Each stage can use a **different model**, skills, and execution budget.
- Each AgentRun gets a **fresh Sandbox**; pushed commits on a shared branch carry work to the next stage.

<!--
The java-ee-to-quarkus workflow, its Agents, and its SkillCards ship as
default content with the operator.
The demo later shows Ian running this workflow against coolstore.

The shipped Agents leave Gateways unset and use the workflow-run selection.
To configure different models, give each stage's Agent exactly one Gateway
and omit the workflow-run Gateway. This is a supported configuration path,
not a claim that the demo uses three models. The workflow-level guide gives
each stage context for the whole task; stage instructions specify its part.
-->

# What we built

Create a run to execute an Agent or workflow:

- **AgentRun** invokes one Agent.
  - Supplies parameters, instructions, a Gateway selection, and execution settings.
  - Creates one Sandbox and reports progress and outcome in Kubernetes status.
- **AgentWorkflowRun** invokes an AgentWorkflow.
  - Creates an AgentRun for each stage, in order.
  - Advances after success; stops on failure or an execution limit.

The **Agent / AgentRun** split follows Tekton's **Task / TaskRun** model.

Available in **Konveyor 0.11**, behind `agentic_enabled`.

<!--
The Agent describes what is available. The run supplies concrete values.
Kubernetes objects let callers create and watch runs through the API.

Different models per stage work through Agent defaults: give each stage's
Agent exactly one Gateway and leave AgentWorkflowRun.spec.gateway unset.
Each child AgentRun then defaults to its Agent's Gateway. For example,
planning and implementation could use different models suited to the work.
An explicit workflow-run Gateway applies to every stage and must be allowed
by each Agent. There is no stage-level Gateway override field today.
This describes the configuration capability, not the model choices in Ian's demo.
-->

# Design constraints

Our CRDs are the building blocks. These choices shape how people use them:

- **Keep the controller generic.** It reconciles runs and Sandboxes; application details belong in the harness.
- **Make runs observable.** Kubernetes holds status; the UI connects directly to the agent pod for live interaction.
- **Control execution.** The harness and runtime enforce budgets and approval settings.
- **Build on Agent Sandbox.** Each workflow stage gets a fresh sandbox; committed files carry work forward.

<!--
The controller passes parameters through without interpreting application
data or calling Hub. It prepares the Sandbox and tracks completion.
The harness is the binary inside the image that sets up the workspace
and launches the agent runtime. A different use case can supply its own.
-->

---

# The Konveyor harness

- Fetches application details and analysis results from Hub
- Clones the repository and prepares the workspace
- Keeps git push credentials out of the agent's environment and git config;
  the agent commits locally, and the harness pushes
- Passes work between stages through committed files on a shared branch

A first pass at credential isolation, informed by **Fullsend**.
**OpenShell** is the next step toward stronger enforcement.

<!--
Fullsend influenced the git-based workspace and credential-handling design:
https://github.com/fullsend-ai/fullsend
https://github.com/konveyor/enhancements/pull/295

Be specific about the boundary: this is git credential handling, not full
isolation of every credential. Provider credentials currently reach the
runtime. OpenShell is intended to add enforced policy and credential
injection outside the agent.

The harness uses a scoped Hub token and revokes it on exit; workflows
share the token until the final stage.
-->

behind a feature flag.

- Add policy enforcement and stronger credential isolation
- Replace our interim Gateway CRD with OpenShell Gateway Services
- Preserve the Agent / AgentRun model as the backend changes

# Where we're headed

**Konveyor helps teams modernize their applications.**

A migration is part of that work. We want to help teams decide what needs
to change, carry out the work, and leave the application easier to maintain
and develop.

That includes preserving the decisions and knowledge gained along the way,
so the team can keep building on the result.
